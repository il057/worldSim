# 模块 01：角色卡清洗与摄入管线规范 (Ingestion Pipeline)

---

## 1. 概述与核心职责

在 SillyTavern（酒馆）生态中，角色卡广泛存在各种针对人机实时对话特化的杂质数据（如内嵌 HTML/CSS、前端脚本宏、强制尾部状态栏指示词以及强依赖 `{{user}}` 的对话模板）。
摄入管线（Ingestion Pipeline）的核心任务是：
1. **剥离所有前端展示性与控制性脏数据**，还原纯粹的角色文学设定。
2. **解除对外部用户 `{{user}}` 的交互依赖**，将交互动机转写为内在心理执念或背景羁绊。
3. **保留并结构化世界书（Lorebook/WorldBook）**：绝不随意截断或大幅压缩世界书内容，完整归类静态背景与动态触发词。
4. **生成角色自适应作息画像（Circadian Profile）**：基于角色身份、种族与生活习惯，动态提取其作息偏好与休眠阈值。
5. **处理多人卡**：识别多实体并引导选定唯一主视角主角（POV Protagonist），将次要实体自动降维为关系网 NPC。
6. **提供纯表单极简创建通道**：基于 4 个基础维度，通过标准化 Prompt 单次衍生出具备同等深度设定的角色数据对象。

## 2. 酒馆卡清洗规则与指导逻辑

AI 开发者在实现清洗模块时，应组织为管道式过滤器（Pipeline Filters），按顺序执行以下剥离操作：

### 2.1 样式与控制标记过滤
- **HTML/CSS 与富文本剥离**：使用正则表达式识别并剔除 `<style>`、`<script>`、`<details>`、`<summary>` 标签及其包含的内容；移除所有裸露的 HTML 容器标签（如 `<div>`, `<span>`, `<p>`, `<br>` 等，替换为合适换行）。
- **酒馆宏与控制标签剥离**：清理 `<START>` 对话标记、前端条件宏（如 `{{random:...}}`、`{{setvar:...}}`）。将 `{{char}}` 占位符统一静态替换为角色自身的真实姓名。
- **状态栏强指令双向剥离**：匹配并剔除“每次回复在末尾附带”、“输出格式必须包含”、`Status_Rule`、`Format_Template`、`{Location, Attire, Time}` 以及所有指示模型打印 ````stat`、````json 或 `[Status: ...]` 状态框的系统提示。该过滤规则同时作用于卡片主体描述与世界书条目。

### 2.2 `{{user}}` 依赖解耦与生态位具象化 NPC 机制
在自主模拟场景中，不存在人类玩家即时输入，且推演主角绝不可识别为抽象的玩家代词。解耦与生态位替代策略：

1. **绝对禁止识别 {{user}} / 玩家 为 POV 主角**：
   - POV 主角实体必须全部是卡片中具名的真实角色。严禁将玩家/User作为推演主角。
2. **只言片语具象化新建 NPC 代替生态位**：
   - 深入分析角色卡与世界书中关于 `{{user}}` 的社会角色或关系纽带（如五人乐队中的鼓手、事务所搭档、监护人、青梅竹马等）。
   - AI 必须根据上下文线索，**具象化新建一个符合世界观背景的具名实体 NPC**（赋予其题材背景下的真实全名，严禁使用“User/玩家/你”），并明确其身份背景与性格。
   - 该具名 NPC 自动注入到所有候选主角的 NPC 社交关系网中，以代替原 user 的生态位。
   - 各主角人设与执念中的 `{{user}}` 依赖彻底转写为对该具象化 NPC 的羁绊与态度，使虚拟世界完全自洽闭环演化。

## 3. 世界书（WorldBook/Lorebook）完整提取与精准分类

酒馆角色卡的世界书通常承载着完整的架空世界法理、地理与势力设定，体量往往达到数千至上万字。**系统坚决不进行粗暴的字数压榨或截断**，而是按照调用机制进行分类落库：

### 3.1 前置拦截清洗与垃圾条目剔除 (Pre-filtering & Junk Elimination)
- **输入端前置精准拦截（大幅缩减 Prompt Token 规模）**：
  酒馆角色卡常夹带数十条纯前端 UI 插件、状态栏排版模板、正则宏替换规则（`s/.../.../`）或越狱覆写指令（`[System Note:]`）。若将这些条目塞给 AI，会导致输入 Token 膨胀到 50k+，首字延迟与处理时间成倍增加。
  系统在向 AI 派发任务前，**通过特征词与正则规则在本地先行动拦截**，彻底杜绝前端插件与代码条目消耗 Token 或被原样挂载入库；
- **原生正文深度解耦与用户清理**：
  世界书条目正文在挂载入库时，强制执行 `clean_text_artifacts` 剔除 HTML/CSS、宏语法，并将正文中残留的 `{{user}}` 彻底替换为替代 user 的具象化 NPC 姓名，并执行 `decouple_user_dependency`，确保入库世界法则 100% 纯净、自洽且不含任何 `{{user}}`；
- 保留所有涉及地理风貌、魔法/科技法则、历史事件、组织势力、物品装备等设定的条目；
- 凡是已被提炼为独立 NPC 的人物条目，不再重复保留在世界书设定表中，消除数据冗余。

### 3.2 世界书 NPC 关系提取与注入
- 当世界书条目标题或正文包含 `NPC_1:`, `Name: ... Relationship: ...` 等人物档案特征时，自动提取结构化社交关系网（姓名、关系类型、好感度、身份背景及对主角态度）。
- 提取后的 NPC 关系自动分配至各主要角色的专属关系网中。

### 3.3 世界书常驻与动态触发精准区隔铁律
系统严格杜绝“常驻世界观又携带触发词”的逻辑矛盾：
1. **静态全局世界观（Static World Lore）**：
   - 特征：标记为常驻生效（`constant: true`）或属于宏观世界法则、自然物理/魔法规则、大时代背景。
   - 规则与约束：**其 `trigger_keys` 必须为空字符串 `""`**！严禁常驻条目填写触发词。推演时全天候无条件加载底色。
2. **动态触发词条目（Dynamic Triggered Lore）**：
   - 特征：包含明确的触发关键词列表（如特定地点名、组织名、专属秘宝）。
   - 规则与约束：**必须包含 1~5 个逗号分隔的精确触发关键词**。通过倒排索引在推演涉及相关词汇时动态激活注入。
3. **后端防御性规整**：
   - 若条目标记为 static，后端强制清空其 `trigger_keys`；若标记为 dynamic 且缺少关键词，尝试以标题补齐或规整为 static，确保分类逻辑 100% 干净。

### 3.4 AI 深度重写世界法则正文与写作风格指导保留 (AI Rewriting & Style Guide Preservation)
- **AI 深度重写与理顺正文（解决机器清洗弊端）**：
  单纯机器正则替换容易导致句子碎裂、前言不搭后语，且酒馆卡中往往将正则宏与设定文字穿插混写。系统在摄入阶段由 AI 统一对保留的世界法则条目进行**深度文学重写与逻辑理顺（输出润色后的 `content`）**，彻底剔除残留代码、宏标记与排版乱码，确保世界法则文字流畅自然、严密自洽；
- **强制保留“写作风格指导”类条目**：
  酒馆卡常包含“写作风格指导”、“文学语调或语言风格”、“描写规范”等条目。系统在输入端设置白名单豁免拦截，并提示 AI 必须将其作为静态常驻（`category: 'static'`，`trigger_keys: ''`）世界法则完整保留并重写，以确保后续小说推演严格继承原卡的文学风格；
- **全链路细粒度超时、流式聚合与防重复计费规范 (Streaming Accumulation & Anti-Double-Billing)**：
  - **流式聚合（Server-Sent Events, `stream: true`）**：针对耗时较长（1~2.5 分钟）的角色卡深度解析与双步推演，客户端强制启用流式聚合。生成期间持续流式接收 SSE 数据块，TCP 套接字在整个传输周期内保持毫秒级数据流动，彻底根除反向代理/网关（Cloudflare、Nginx、OneAPI/NewAPI 等）因 60s 空闲超时主动发送 TCP FIN/RST 掐断连接（引发 `Server disconnected without sending a response`）的问题；
  - **严格杜绝二次重试扣费（Zero Double-Billing Defense）**：在 HTTP 客户端层严格隔离重试边界。**仅在 TCP 握手阶段（`ConnectTimeout` / `ConnectError`）允许安全重试**（此时未向服务端成功发送请求，Token 消耗为 0）；凡是请求已发出、服务端可能已扣费的错误（如 `RemoteProtocolError`、`ReadTimeout` 或流式中途中断），**严禁自动无脑重试**，并在日志与错误响应中明确提示用户，从根本上杜绝服务商针对同一高额任务多次扣费。
  - 前端将解析接口超时独立提升至 600 秒（10分钟），避免前端误报网络超时。

## 4. 角色基础档案、动态周岁与作息画像 (Identity, Dynamic Aging & Circadian)

系统坚决杜绝死板的一刀切作息表与硬编码写死的角色年龄：

### 4.1 基础生理档案独立存储与人设纯净规范 (Persona Token Optimization)
在角色摄入阶段，由 AI 提炼出结构化的核心生理档案：
- **独立基础生理字段（First-class Keys）**：
  - **生理/社会性别（Gender）**：男 | 女 | 非二元 | 无性别/未知；
  - **诞生时间/生日（Birthday）**：必须包含具体年份与月日（如 `2007年3月15日` 或架空纪年 `天禧二年五月初三`）。系统在推演时结合当前虚拟时间与该生日**动态推演实时真实周岁**，彻底消除“世界演化数年后角色年龄依旧是硬编码写死”的荒谬现象；
  - **外貌体征（Appearance）**：身高、体型、发色瞳孔、标志性体貌特征与常驻装束穿搭；
- **消除 Persona Summary 冗余与 Token 浪费**：
  - 由于性别、生日与外貌已具备独立专属字段存储，系统在 Prompt 与后处理中严禁在 `persona_summary` 重复拼接 `【基础档案】` 等冗余生理标签；
  - `persona_summary` 100% 深度倾注于：角色深刻的核心性格底色、为人处世哲学、行事准则、心理防御机制、行为癖好、人际交往态度与深层人物背景脉络；
- **生理节奏倾向（Chronotype）**：如 `早起型`、`夜行型`、`昼夜无律型`、`无休眠体质`；
- **常规休眠倾向窗口（Typical Rest Window）**：例如 `05:00 - 13:00`；
- **开局微观具体地点（Initial Location）**：基于角色常驻居所或开局情境推导（如“长宁市古董街老宅正堂”），绝不使用通用占位字符串；
- **开局确切虚拟时间（Initial Virtual Time）**：必须包含准确的【公历或纪年年、月、日、时:分】（如“2024年10月9日 20:15”或“天禧三年十月初九日 20:15”），后端具备日期校验与自动规整防御；
- **随身背包与紧迫目标**：自适应提取符合职业背景的 3~5 件随身物件与 2~3 条紧迫目标。

## 5. 多人角色卡识别、世界书 NPC 全量摄入与独立关系网 (Multi-Entity & Independent Networks)

### 5.1 多实体识别与所有登场 NPC 平等深度双轨描写铁律
- 酒馆多人卡的人设普遍定义在世界书条目或主体描述中（如乐队成员、公馆住客）。
- 解析引擎识别所有主要角色实体并输出在 `entities` 中，供用户单选确立主视角（POV Protagonist）。
- **顶级世界书配角提取通道（`world_npcs`）**：
  - AI 全量扫描世界书条目，将所有描述具名人物、次要角色、导师、对手、反派干部的条目全部提炼为顶层的 `world_npcs` 列表；
  - 被提炼为 NPC 的世界书条目不再保留在 `kept_lores` 纯文本中。
- **所有登场 NPC 平等深度双轨描写铁律（绝对禁止厚此薄彼与单句敷衍）**：
  - 无论在原角色卡中是并列主要角色、世界书配角、还是替代 user 的生态位角色，作为 NPC 呈现时**地位与深度绝对平等**；
  - 绝对禁止因某人在原卡中是主要角色就以为“大家都认识”而偷懒只写一两句主观感受（如仅写‘嫌弃对方身上浓重腥气’这种残缺单句），也绝对禁止只写背景不写态度；
  - 每一个 NPC 的 `summary`（身份背景与对主角态度）统一遵循规范的【双轨深度结构】：
    1. **【人物身份背景与核心性格特质】**：客观写明该人物在世界中的真实社会身份/职业/核心能力特征、行事风格与性格底色（提供独立完整的小像，严禁写‘本卡主要角色’等元标签）；
    2. **【主视角态度与羁绊纠葛】**：深入写明当前主视角主角对其的真实主观态度、评价、好感成因、互动习惯或过往恩怨；
  - **后处理智能融合双保险**：后端自动将其他主要候选实体的客体 `persona_summary` 与主视角对其的专属态度进行智能融合拼接，彻底根除任何单句敷衍与厚此薄彼现象。
- **三位一体关系网确定性聚合保底**：
  - 每一个候选实体在生成完成后，后端自动将其专属视角关系网聚合保底：
    1. **其他主要候选实体**：降维互为主要同行者（客观完整小像 + 主角专属羁绊态度）；
    2. **世界书提取的全量配角 NPC（`world_npcs`）**：确保世界书中数十位配角全部注入到候选主角关系网中，杜绝因大模型注意力瓶颈导致配角遗漏；
    3. **替代 {{user}} 的生态位具象化 NPC**：保持社交生态严密闭环。
- **严禁字数截断与禁止元描述废话铁律**：
  - 无论在 Prompt 还是 Python 后端代码中，彻底移除任何形式的字数截断切片，保证 NPC 人设与态度评价充实完整；
  - 严厉禁止在描述中出现“本卡的主要人物”、“卡片主角之一”、“主要同行者”、“系统生成的NPC”等跳出世界观视角的机械元标签，每一个字均纯粹立足于世界观之内描写其真实的身份、性格与羁绊。
  - 前端微调面板在切换主角单选时，**人设、生理状态与全量 NPC 关系网全联动切换**，呈现该角色专属视角。

### 5.2 降维处理机制
选定主主角后，其余未选中的主要实体与世界书 NPC 共同作为该主角专属关系网中的核心 NPC 存在：
- **主角实体**：承载核心状态看板、三层记忆与自主推演镜头，作为故事演化的绝对有限视角焦点。
- **降维 NPC**：继承其专属好感度、社会关系类型与态度评价，写入社交关系表（`character_relationships`），并在开局快照中完整持久化。

## 6. 导入前全维度审查与手动微调系统 (Pre-Import Inspector)

摄入管线坚决不进行黑盒强制落库，解析完成后向用户提供 4 维度的新拟态深度微调面板：
1. **人设与执念**：
   - 专属头像管理：支持自由上传本地自定义头像图片（转换为 Base64），或一键重置为系统默认占位头像；
   - 基础生理档案：支持审查与微调角色性别、诞生时间/生日（动态周岁基岩）、外貌特征与标志装束；
   - 角色姓名、头衔、内在执念与**全量不截断的完整人设**（支持自由增删与修饰）；
2. **生理与初始状态**：开局地点、虚拟时间、健康值滑块、精力值滑块、即时心理、作息画像、背包物品增删及目标增删；
3. **NPC 关系网**：针对当前选定主角视角，可视化查看与编辑专属 NPC 关系（支持编辑姓名、好感度与背景，支持手动新增或移除 NPC）；
4. **世界书设定**：清晰展示已保留的干净世界书条目，支持动态关键词触发/静态常驻世界观类型自由切换、触发词修改以及条目增删。

落库时，系统以用户最终确认微调后的全部参数为准统一提交持久化。

## 6. AI 智能角色构思与世界衍生通道 (Quick Character & Blueprint Generator)

针对无预置酒馆卡的用户，系统提供极简且高度自由的衍生通道（所有输入字段均可选，未填由 AI 自主原创推演）：
1. **基础锚点（均为可选）**：角色姓名、身份/职业、性别倾向（`NeuSelect` 下拉）、生日/历法纪元、外貌特征描述、性格底色；
2. **核心引导（世界观与社交网络指引）**：多行自然语言文本框，支持用户以一两句话勾勒人际网络与世界轮廓（例如：“ta喜欢恶作剧且讲义气，近期目标是帮同桌追到校草；学校是海滨私立高中”）；
3. **开局处境**：微观初始场景或冲突。

**AI 衍生核心准则（Prompt Invariants）**：
- **基调自适应铁律**：严禁将轻松、日常、校园、幽默或治愈题材强行黑化为沉重苦大仇深。
- **内在执念去沉重化**：核心执念（`inner_drive`）拒绝公式化的“童年创伤/遗弃恐惧/心理病态”，鼓励源于少年意气、热爱追求、承诺信条或探索好奇。
- **立体可爱的人性**：角色缺陷是生活化的小毛病或反差萌（如爱逞能、嘴硬心软、做事三分钟热度等），而非严重精神疾患。
- **社交网络张力**：根据题材自适应生成 2~4 位初始 NPC，校园中涵盖损友、校草、严厉班长等（好感度 -30 到 90 浮动，负好感体现拌嘴互掐而非血仇）。
- **渐进式审查（Progressive Disclosure）**：调用 `POST /api/v1/characters/generate-blueprint` 产出结构化蓝图并自动装载进预审面板，用户确认无误后方落库开局。

## 7. PNG 角色卡内嵌解析与头像提取规范

系统全面兼容 SillyTavern 与主流酒馆生态的标准 PNG 角色卡（内嵌元数据）：
1. **二进制 Chunk 检索**：服务端解析 PNG 字节流中的 `tEXt`、`zTXt`、`iTXt` 数据块，定位关键词为 `chara` 或 `ccv3` 的内嵌数据；
2. **Base64 解码与反序列化**：对数据段进行 Base64 解码并提取 UTF-8 JSON 角色卡主体与世界书；
3. **高清头像无缝保留**：直接将上传的 PNG 编码为 `data:image/png;base64,...` 数据 URL，写入角色的 `avatar_url` 属性中，确保在 UI 看板、角色名录与弹窗中无缝呈现。
